# eat-patch

ライセンス判定が native DLL 側にある .NET アプリに対する、プロセス内 EAT パッチ。

[English](README.md) | [中文](README.zh-CN.md) | **日本語**

対象のアプリは、マネージドな WinForms の外殻と 1 つの native ライセンス DLL で
できています。面白いロジックは全部 DLL 側にあり、マネージド側は 18 個の
`DllImport` を宣言してウィンドウを描いているだけです。このリポジトリは、その
ために書いた起動ツールです。アプリを普通に起動し、メモリ上で DLL のエクスポート
アドレステーブルを書き換え、ライセンス関連の呼び出しに既定値を返させます。
ディスク上のファイルには一切触れません。

汎用のアンパッカーではありません。別のアプリにそのまま使っても動きません。
「一つの実例 + 再利用できる stub のレイアウト」として読んでください。

## なぜメモリ内なのか

素直な方法は、この対象では全部通用しません:

| 試したこと | 結果 |
|---|---|
| マネージド IL の書き換え | 15638 個のメソッド本体のうち 13019 個が 4 バイトの空 stub（`nop nop ldc.i4.1 ret`）。書き換える中身がない |
| ディスク上の DLL を編集 | 1 バイト反転でも 1 バイト追加でも、約 1.1 秒で `rc=0` のまま終了。ウィンドウも .NET イベントログも残らない |
| 同じエクスポートを持つ代理 DLL に差し替え | 同じく無言で終了 |
| `App.exe.local` によるリダイレクト | 無視される。Win7 以降、manifest での宣言がないと効かない |

途中で 2 つの可能性は潰しました。PE checksum（`stored=0x0` で元から未設定）と、
埋め込まれたハッシュ（ファイル全体と各セクションの md5/sha1/sha256/crc32 を、
raw と hex の両形式で 32 MB の exe 全体から検索 — ヒット 0）。残るのは「全バイト
＋正確なファイル長」を見る検査で、失敗時は例外ではなく `Exit` を呼ぶ、という
説明だけです。したがって立てる場所は、検査が通過した後のプロセス内部しかあり
ません。

## 仕組み

**stub blob**（`src/stub.asm`）は `nasm -f bin` の出力で、位置非依存です:

```asm
BASEP:
    push ebx
    call %%a
%%a: pop ebx
    sub ebx, %%a
```

各 stub はこの方法で blob 自身のアドレスを `ebx` に得ます。だから注入側は
`VirtualAllocEx` でどこに置いてもよく、リロケーションも要りません。

**名前ではなくスロット。** stub は `f00`..`f29`、cfg ワードは `c00`..`c15`、
実アドレススロットは `r00`..`r29`、文字列は `s0`..`s6`。両者は EAT のインデックス
だけで対応するので、ソースに対象固有の識別子は出てきません。注入側は
エクスポートアドレステーブルを序数でたどり、名前文字列は読みません。

**転送は jmp でなければならない。** 両側とも stdcall です。`call` して戻ると
引数が二度 pop され、`0xC0000005` になります:

```asm
mov eax, [ebx + r21]
pop ebx
jmp eax
```

**r スロットは入口ではなくトランポリンを指す。** 入口の 5 バイトは `E9` そのもの
なので、r スロットを入口に向けると転送が即座に stub へ戻ってしまいます。thunk 形
（`56 57 53 E8 rel32 5B 5F 5E C3`）の実体は `entry + 8 + rel32`。それ以外は、
追い出したプロローグを blob に写し、中の `E8`/`E9` の相対変位を直し、末尾に
`E9` を足して `entry + n` に戻します。小さな x86-32 命令長デコーダが必要で、
`launch.cs` の `DisplacedLength`/`InstrLength` がプロローグに実際に出る命令を
カバーしています。

**自己記述シンボルテーブル。** blob の末尾は `PAKB`、個数、83 個の dword。
注入側はファイル末尾から逆算して見つけます。`stub.asm` を編集しても注入側を
触る必要がなく、古いオフセットが別のワードを静かに壊すこともありません。

## 時間を使った 2 点

`f13` は文字列解放関数です。呼び出し側は受け取ったポインタを必ず解放しますが、
用意した文字列は DLL のヒープではなく blob 内にあります。そのまま本物の free に
渡すとヒープが壊れ、プロセスは即死します。stub はポインタが
`[blob, end_of_block)` に入っているかを先に判定し、入っていればローカルで返します。

`f06(2)`、`f06(3)`、`f06(4)` は呼び出し側で `Double.Parse` されます。空文字列を
返すとメッセージループの中で例外になり、目に見える症状は「パッチは当たった、
ライセンスも通った、でもメインウィンドウが出ない」です。パッチが効いていないと
誤解しやすいところでした。この 3 つに数値を入れればウィンドウは出ます。

## ビルド

`nasm` と .NET Framework のコンパイラが必要です。どちらも普通の Windows に
入っています。

```bat
build\build.bat
```

手動なら 2 ステップ:

```bat
nasm -f bin -l build\stub.lst -o build\stub.bin src\stub.asm

%WINDIR%\Microsoft.NET\Framework\v4.0.30319\csc.exe ^
  -nologo -target:winexe -platform:x86 -optimize+ ^
  -out:build\launcher.exe ^
  -resource:build\stub.bin,stub.bin src\launch.cs
```

`-target:winexe` が重要です。exe サブシステムだとコンソールが開いてしまいます。
winexe なら完全に無言で、失敗時だけ `MessageBoxW` が出ます。

## 使い方

```
launcher.exe                    無言: 起動 → 注入 → トリガー → 最前面解除 → 終了
launcher.exe --verbose          コンソールを残して 4 ステップを表示
launcher.exe "D:\path\to\app"   ディレクトリ指定。1 階層下のサブディレクトリも探す
```

実体の判定はサイズで行います。同じ名前で配られるインストーラは約 52 MB なので
飛ばされます。native DLL と `Resources` フォルダが隣にあることも条件です。
見つからなければ無言で失敗せず、メッセージボックスで知らせます。

## 別の対象に向ける

`src/launch.cs` の先頭 2 つの定数:

```csharp
const string AppName   = "TARGET";
const string TargetDll = "AUTH.dll";
```

そのうえで `src/stub.asm` のスロット表を対象のエクスポートに合わせて書き換え
ます。どのスロットをローカル応答にするか、引数が何バイトか、cfg ブロックの並び
はどうか。`launch.cs` の `CfgOn` と `StrInit` がスロット番号で挙動を選びます。

## 既知の制限

- 32 ビットのみ。対象が x86 で、注入コードも x86 です。
- エクスポートテーブルは小さく、転送エントリがないこと。
  序数による走査は `AddressOfFunctions[i]` が素の RVA である前提です。
- 1 つの対象、1 つの Windows ビルドでしか検証していません。起動後にメモリページを
  再保護するパッカー下での挙動は未検証です。
- `--verbose` でも対象アプリ自身のウィンドウ癖は残ります。メインウィンドウには
  キャプションがなく（`style=0x16030000`）、`SWP_NOSENDCHANGING` なしでは外部からの
  移動を拒否します。
