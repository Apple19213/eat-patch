# 技术分析：从托管层全空到进程内 EAT 补丁

记录完整判断链路：每一步做了什么、为什么这么做、什么证据推翻了什么假设。

---

## 0. 目标与已知条件

一款国产商业工具（下称 TARGET，.NET WinForms，主程序约 32 MB），启动即弹「登录」窗，需账号或授权码。附带一个 native 授权 DLL（下称 AUTH.dll，约 1.4 MB）。

目标：不输入授权码直接进入主界面，全部功能可用。

---

## 1. 先看托管层：为什么改 IL 没用

`ilspycmd -p` 反编译出 1159 个 .cs、43 MB。特征：

- 类名/字段名随机化（`A0V7DNekoTbO90lxXA9d`）
- 控制流平坦化（`num/num2/num3` 状态机）
- 存在两个 `<Module>{GUID}` 类型

关键观察：**方法体基本是空的**。

```
TARGET.Form120 里 10384 个方法体是 Code size: 4
  → nop; nop; ldc.i4.1; ret     （返回 true）
  → nop; nop; ldnull; ret       （返回 null）
```

用十六进制直接核对磁盘字节，确认不是反编译器失真：

```
... 13 30 04 00 04 00 00 00 00 00 00 00 00 00 17 2a ...
      ^^^^^ method header         ^^^^^^^^^^^ code: nop nop ldc.i4.1 ret
```

**结论**：保护器把方法体抽空/替换了。静态改 IL 无从下手。

方法体尺寸统计（正确解析 PE 节头后）：

| 类别 | 数量 |
|---|---|
| 无效/空壳（code size ≤ 4） | 13019 |
| 真实可执行 | **2619** |

而 `Form120` 只有 11 B 真实 IL（就是那 18 条 `DllImport` 声明）。

> 踩坑记录：早期解析节头时把 `Name(8)+VirtualSize+VirtualAddress+SizeOfRawData+PointerToRawData` 的字段顺序写错，把 `VirtualSize` 当 `VirtualAddress`，导致算出 "2.8e11 字节真实 IL" 这种荒谬结果。正确写法是 `struct.unpack_from('<IIII', d, secoff + i*40 + 8)` → `(vs, va, rs, ro)`。

---

## 2. 找到真正的授权入口：18 个 P/Invoke

全程序集搜索 `pinvokeimpl`，只有一处：

```csharp
[DllImport("AUTH.dll", CharSet=Ansi, ExactSpelling=true, SetLastError=true)]
public static extern int f21——试用();
public static extern int f24(ref string, ref string);
public static extern native int f06——信息查询(int);
public static extern native int f20——提示串();
public static extern native int f14——到期时间();
// ... 共 18 个
```

**这是整个逆向的转折点**：托管层只是 UI 壳，全部授权判断在 native。

参数语义也已确定：

- `string& marshal(byvalstr)` = 调用方分配缓冲区的 out 参数
- `native int` 返回值 = **DLL 分配的 ANSI 字符串指针**，用完须 `f13——字符串释放`

## 3. 第一次尝试替换 DLL，失败

| 实验 | 结果 |
|---|---|
| 原版 DLL | 正常启动，登录窗出现 |
| 改名换掉整个 DLL | `0xE0434352`（CLR 未处理异常，DllNotFoundException） |
| 原版 + 1 字节 XOR | **`rc=0`，1.10 秒静默退出，无窗口无日志** |
| 原版 + 1 个 0 字节 | **`rc=0`，1.10 秒静默退出** |
| 只改 `.rsrc` slack 里的死字节 | 同样秒退 |
| 自写 30 导出全转发代理 | 同样秒退 |

推论链：

1. 不是 PE checksum —— 原版 `stored=0x0`，本来就没填。
2. 不是内置静态哈希 —— DLL 的 md5/sha1/sha256/crc32 及各节哈希，以 raw/hex/HEX 多种形式在 exe 全文（32 MB）搜索，**0 命中**。
3. 不是 DLL 自校验 —— 把被篡改的 DLL 改名成别的文件给独立 probe 加载，一切正常。
4. 校验覆盖**整文件全部字节 + 精确长度**，且失败时静默退出（不抛异常，直接 `Exit`），所以事件日志也查不到。

**结论**：文件级任何改动都不可行，必须走进程内存。

## 4. 内存补丁架构

### 4.1 改写 EAT

`AUTH.dll` 导出目录 rva `0x38100`，30 个导出。两种入口形态：

| 形态 | 特征 | 数量 |
|---|---|---|
| thunk | `56 57 53 E8 rel32 5B 5F 5E C3` | 9 |
| 直接封装体 | `56 57 53 8D 74 24 10 83 EC ..` | 21 |

统一处理：入口前 5 字节改成 `E9 rel32` 跳到我们的 stub。

### 4.2 stub blob

`nasm -f bin` 生成位置无关 blob（约 10 KB），`VirtualAllocEx` 到目标进程。

三个设计决定：

**自定位** —— 每个 stub 用 `push ebx / call .a / .a: pop ebx / sub ebx,.a` 拿到 blob 基址，因此 blob 可落在任意地址。

**转发用 jmp** —— stub 是 stdcall（`ret N*4`），目标也是。`call` 进去再 `ret` 会二次弹栈，现象是 `0xC0000005`。必须：

```asm
mov eax, [ebx + real_f21——试用]
pop ebx
jmp eax
```

**自描述符号表** —— blob 尾部 `'PAKB' + count + 83 个偏移`。注入器运行时读表，改 stub.asm 后不必同步改注入器。

### 4.3 第一次跑通，但无限递归

给 `real_*` 填 `base + rva`（即**已经被我们改过的入口**）→ stub 转发跳回入口 → 入口跳回 stub → 递归。

修法：按形态构造 trampoline。

- thunk：`real = entry + 8 + rel32`
- 直接体：抄前 `DisplacedLength(code)` 字节到 blob 内，重算 `E8/E9` 位移，末尾补 `E9` 回 `entry + n`

`DisplacedLength` 需要一个最小 x86-32 长度解码器（覆盖 `push/pop`、`8D 74 24 xx`、`83 EC xx`、`B8-BF`、`E8/E9/EB`、`0F 8x` 等常见序言即可）。

## 5. 三个把主界面卡住的坑

### 坑 1：`f13——字符串释放` 释放了我们的静态串

让 `f20` 返回一句看起来成功的文案 后程序当场死。原因：`f20——提示串()` 返回 blob 内静态缓冲，调用方按约定 `f13——字符串释放(ptr)`，真实实现去 `free` 一块不是 malloc 来的内存。

修法：`f13——字符串释放` 先判指针是否在 `[blob, blob_end)`：

```asm
mov eax, [esp + 8]
cmp eax, ebx
jb  .forward          ; 低于 blob → 真实 DLL 的
lea ecx, [ebx + blob_end]
cmp eax, ecx
jb  .local            ; 落在 blob 内 → 我们的，直接返回
```

### 坑 2：`f06——信息查询(2/3/4)` 被 `Double.Parse`

补丁生效、`Right` 也构造成功，但主界面不出来。登录窗里藏着一个未处理异常提示：

> 从字符串""到类型"Double"的转换无效。

`f06——信息查询(1)` 是软件公告文本，但 `f06——信息查询(2/3/4)` 是数字字段。改成 `99999` 后主界面立刻出现。

### 坑 3：窗口在屏幕上但"看不到"

进程在跑、`IsWindowVisible=1`、`cloaked=0`、截图证明内容已渲染 —— 用户仍说看不到。原因三条叠加：

1. 主窗 `style=0x16030000`，**没有标题栏和边框**，看着不像窗口
2. 启动器 800ms 就退出，控制台一闪而过
3. 旧代码 `SetWindowPos(HWND_TOPMOST)` 后紧接着 `HWND_NOTOPMOST`，等于立刻把刚置顶的窗口压回控制台后面

另外主程序在 `WM_WINDOWPOSCHANGING` 里拦截外部移窗（`SetWindowPos(...,0x40)` 返回 **0**）。必须带 `SWP_NOSENDCHANGING(0x0400)`，之后返回 1、rect 立刻改变。

## 6. 最终验证

调用序列（成功路径，13 条）：

```
f21——试用 → f06——信息查询(2) → f13——字符串释放 → f06——信息查询(1) → f13——字符串释放
     → f06——信息查询(3) → f13——字符串释放 → f06——信息查询(4) → f13——字符串释放
     → f20——提示串  → f13——字符串释放 → f14——到期时间 → f13——字符串释放
```

注意 `f02——轮询时钟` 是高频轮询（会瞬间灌满 256 条日志环形缓冲），`f01` 也是，日志里必须跳过或去重，否则看不到真正的一次性调用。

运行时校验：

```
f21——试用          e9196581fc75fdff  PATCHED
f20——提示串           e9b16581fcf2ffff  PATCHED
f06——信息查询        e9e56b81fc241083  PATCHED
f08          e9e46481fccaffff  PATCHED
```

稳定性：600 秒 / 10 秒采样共 55 个点，无重鉴权、无掉授权、无崩溃。磁盘 `AUTH.dll` md5 全程不变。

## 7. 可复用的经验

1. **先确认逻辑在哪一层**。托管层方法体全空 → 立刻转 native，不要在 IL 上浪费时间。
2. **校验粒度要实验测定**，不要靠猜。改 1 字节 vs 加 1 字节 vs 改 slack，三种实验就能定位"整文件+长度"。
3. **静默退出比异常更难查**。`rc=0` 且无事件日志，说明对方主动 `Exit`，这时唯一的路是绕开检查点（进程内）而不是绕过检查逻辑。
4. **stdcall 转发只有 `jmp` 一种正确写法**。
5. **自描述数据段**省掉大量"改一个宏就全线偏移"的调试时间。
6. **构造返回值要服从调用方的类型契约**。空串对 `Double.Parse` 是炸弹。
7. **UI 层的"看起来没生效"经常是窗口可见性问题**，不是补丁问题 —— 先用 `IsWindowVisible` + 截图 + 像素统计分开判断。
